# CLAUDE.md

Working notes for AI-assisted sessions in this repo.

## What this is

thingGLANCE: the GLANCE family's tracker for things that carry dates (warranties, subscriptions, support windows, planned replacement). Sky blue. Web app + PWA, an Android app (Capacitor 8, `android/`, app id `com.thingglance.app`) with GLANCElauncher integration, an iOS app (Capacitor 8, `ios/`, the same app id) and a desktop app (Electron, `electron/`) with a tray, reminders, an MCP server and a Stream Deck plugin (`stream-deck-plugin/`). It will be a paid app ($9.99) with no paywall, so there is no billing code. It is NOT a home inventory: resist features that only catalogue.

Sibling repos sit next to this one (`../lastGLANCE` is the closest model: same stack, TypeScript, Dexie, Tailwind). When wiring anything family-shaped (vault, roster, intents, shells), read how lastGLANCE does it first and match the wire contract.

## Conventions

- **Sync is GLANCEvault only.** Do not add WebDAV, iCloud or Direct Access roads.
- **`src/core` stays pure**: no React, Dexie or DOM imports. Widgets, the tray, MCP and headless runs will import it.
- **One write path**: every local mutation goes through `src/db/queries.ts`, which stamps `updatedAt` and calls `markDirty`. Remote applies in `src/sync/dbEngine.ts` write to Dexie directly and must never call `markDirty`.
- **Local shape == sync shape.** UUID ids double as vault entity ids; every synced entity has a `kind`. The only local-only field is `sample`.
- **Household members**: before touching owners, payers, the roster or who gets alerted, read `docs/household-members.md` (the spec, how it differs from the code, and what was built). The `glance-users` row stays `{ id, name, updatedAt }`: sibling apps erase anything else put on it. A user is a member with a `device` row; each device writes only its own. There is no multi-user switch: `multiUser` in the data context just means the roster has more than one member, and the roster syncs whenever the vault is on.
- **Privacy is applied once, at the door.** `visibleTo()` (`src/core/household.ts`) strips other members' private items in `DataProvider` and in `buildSnapshot()`. Build new surfaces from those, never from the raw tables.
- **Every row that comes in is read through `src/core/shape.ts`** (Dexie upgrade, vault apply, backup import), so v0.1 rows are carried forward. Add a reader there when a synced field is renamed.
- **Sample rows never sync.** `toSync` answers null for them; editing one promotes its whole family (thing + coverages + plans) via `promoteFamily`.
- **Other surfaces read `buildSnapshot()`** (`src/core/snapshot.ts`). Its shape is a frozen contract: read `docs/snapshot.md` before touching it. Adding a field keeps the version; anything else bumps `SNAPSHOT_VERSION`. `snapshot.test.ts` pins the field lists.
- **A plan's days and costs come from `src/core/money.ts`**, never from a cycle expanded somewhere else. `renewalsBetween()` is the one place a plan renews: from its start date (`planStart()`: the day it was entered, for a plan with none on record) and before its end date. A plan that renews and has an end date is a fixed term (a lease, installments): `termEnd()`, with its last day on the horizon as a `sub-end`. Anything that counts plans or their cost asks `isOver()` / `isBilling()`, not `status` alone.
- **Reminders are decided in `src/core/reminders.ts`**, never in a shell. A shell only makes the platform's pending notifications match `planReminders()` (also in the snapshot as `reminders`). On Android that matching is native (`android/.../reminders/`), fed by the snapshot, so it also works with the app closed; do not schedule from the web side. The desktop is the same: the main process schedules from the payload the page hands it (`electron/reminderScheduler.ts`).
- **The iOS app is a shell like the others** (`docs/ios.md`). Its plugins are registered by hand in `ios/App/App/BridgeViewController.swift`: one left out is undefined on the web side. What the app and its extensions share lives in the Swift package `ios/App/Packages/GlanceKit` (the App Group store, the queue of outside writes, the reminder plan), Foundation only, tested by `npm run test:ios`. The widgets (`ios/App/GlanceWidgets`, iOS 17) draw from the payload through it and count the days themselves. A button on a notification or a widget only queues a write there; the app applies it. A link made outside the page (a quick action, a shortcut, the Control Center button, a share) is written down there too and taken by `followQueuedLinks()`; it reaches `openLink()` like any other and never changes data. Versions come from `scripts/sync-ios-version.mjs`, never from Xcode's General tab, and `capacitor.config.ts` keeps `ios.handleApplicationNotifications` false so the app's own reminder handler stays the delegate.
- **A background refresh is an allowlist** (`src/headless/`, `android/.../refresh/`): the same bundle with no screen, run by Android a few times a day. It starts only what its list needs, and its bridge has only the methods in `HEADLESS_BRIDGE_METHODS`. Anything new it should do goes on both lists. It must never run while the app's own page exists.
- **Two doors in from outside, and they stay separate** (`docs/links-and-intents.md`). A link (`src/core/links.ts`) only navigates and is acted on in one place, `src/state/useLinks.ts`: never add a link that changes data. A write from outside goes through `handleIntent()` (`src/intents/`), must carry a `clientId`, and is applied once. A shell calls `openLink()` or `dispatchExternalWrite()` and nothing else.
- **Automation apps (Tasker) ride the widgets' queue** (`android/.../automation/`, `docs/tasker.md`). The receiver only queues `{ action, payload, clientId }` and broadcasts the answer the app hands back with `acknowledgeWrites`; it applies nothing itself, and does nothing at all until the user turns the switch on in Settings. `QUERY` is answered from the stored snapshot; `OPEN` is a link.
- **GLANCElauncher reads the widgets' payload and writes through the widgets' queue** (`android/.../launcher/`, `docs/launcher.md`). The provider serves rows mapped out of the stored payload, so add what the launcher needs to the payload (`launcherBlock()` in `src/native/widgetBridge.ts`), not to a second store. The receiver only queues `DECIDE` and `SEND` and routes `REFRESH`; it sends no answer (the launcher reads `meta.handledWrites`). `launcher_certs.xml` lists the launcher's certificate, never thingGLANCE's own. The `meta` field names are shared with dayGLANCE and lastGLANCE: do not rename one.
- **"Owned since" is a record, not a check** (`docs/release.md`, `src/core/ownership.ts`, `android/.../ownership/`, `electron/ownership.ts`). Only a store shell reports a purchase (Google Play's, the Mac App Store's); never write one from the web app, and never read one to allow or refuse anything. `thingglance_owned.xml` is the one preferences file that stays in Android's backup: do not add it to the exclusions.
- **Every request goes through `src/sync/shellFetch.ts`** (`netFetch`, or `fetchImpl: shellFetchImpl()` on a vault client or sync engine). No bare `fetch()`: a shell cannot carry a request it cannot see, and `shellFetch.test.ts` fails on one.
- **An iPhone's device id is decided by the Keychain** (`src/sync/deviceIdentity.ts`, `docs/ios.md` under Backups). A backup carries the page's storage to another device and not the Keychain, so a copy whose id the Keychain does not know takes a new one at boot and drops what is left of the connection. `settleDeviceIdentity()` runs before `hydrateSecrets()`; anything a shell starts that reads the device id waits for it, and nothing writes the id but `deviceId.ts`.
- **Credentials go through `src/sync/secrets.ts`, and the root key config is always `dbCryptoConfig()`** (`src/sync/keyHooks.ts`). Never read or write the vault config in localStorage directly. Never call a shell's keystore directly either: `secureOp()` is what gives every call an order and a deadline. `docs/shells.md` lists every seam a shell uses.
- **The desktop app is a shell like the others** (`docs/desktop.md`). `src/native/desktop.ts` is the bridge's contract and `src/native/desktopShell.ts` hands its pieces to `registerShell()`; app code never asks whether it is on the desktop to make a request, read a credential or follow the live stream. A new bridge method goes in three places (the interface and `DESKTOP_BRIDGE_METHODS`, `electron/preload.cts`, a handler in `electron/`), and `electron/bridgeContract.test.ts` fails on two out of three. Every handler checks its sender. The origin `app://thingglance` never changes: the data is keyed by it.
- **The desktop page makes no request of its own.** Its CSP is `connect-src 'self'` (`electron/csp.ts`); the main process makes every one and refuses a private address until the user allows that origin (`src/sync/privateAddress.ts`). Do not widen the CSP to make something work: route it through `netFetch`.
- **The desktop's main process never opens the database or runs sync.** The tray, the reminders and anything else outside the window are drawn from the payload the main window pushes (`startDesktopFeed()`), and change data only by queueing a write the page applies through `dispatchExternalWrite()` (`electron/commandQueue.ts`), as an Android widget does. The tray popup (`?tray=1`) is a widget too: `main.tsx` starts no shell for it.
- **The MCP server answers as this device's member, and never deletes** (`docs/mcp.md`, which is also the tools' contract: the transport test reads the tool names from it). It holds no data: every tool asks the page over the request bridge, reads go through `readData()` (so `visibleTo()` has already run), and changes go through `src/db/queries.ts` or `dispatchExternalWrite()` and answer with an undo record. A new tool goes in the doc, in `electron/mcpReadTools.ts` or `mcpWriteTools.ts`, and in `src/mcp/`. The "Set up Claude Desktop" button (`electron/mcpDesktopSetup.ts`, `mcpDesktopConfig.ts`, the bundled `@glance-apps/mcp-bridge`) is left out of the Mac App Store build: never import either module statically, and keep the button behind `__MAS_BUILD__`.
- **The Stream Deck plugin is a second package** (`stream-deck-plugin/`, `docs/stream-deck.md`) with its own lockfile. It shares one file with the app, `electron/deckProtocol.ts`, which must stay free of Node and Electron. What a key shows is a pure function in `src/keys.ts`; the keys read what the tray reads (`electron/deckModel.ts`) and a press goes through the command queue. Its tests run with the app's, and `npm test` generates its icon table first.
- **Files under `electron/` copied from lastGLANCE or dayGLANCE say so in their first line.** Keep a fix in step with the sibling it came from, as with the wire contracts.
- **Colours are CSS variables** (`src/index.css`) mapped in `tailwind.config.ts`. Use the semantic names (`bg-panel`, `text-dim`, `text-accent`, `ok` / `warn` / `bad` / `sub`), never raw palette classes, so light and dark stay one set of class names.
- **No text in code.** Every word on screen comes from `src/locales/en/translation.json`: `t()` from `useTranslation()` in a component, `tr()` from `src/core/text.ts` anywhere else, called when the text is needed and never at module load. Dates and numbers go through `fmtDay` / `fmtMoment` / `relative` / `money`, never `dayjs().format()` with a display pattern. Read `docs/i18n.md` before adding a string or a language; `locales.test.ts` fails on a key that is missing or unused.
- **Live push is additive.** `src/sync/vaultEventStream.ts` only ever triggers the same drains the polling cadence runs. Never make anything depend on a nudge arriving.
- **A passphrase is proven against the sibling apps before it is trusted** (`src/sync/keyCheck.ts`). The sync engine only checks a key against the app's own namespace, which is empty when thingGLANCE joins an existing account, so on its own it accepts any passphrase. Never call `engine.ensureRootKey()` on a new passphrase without that check first.
- **Vault intents are always encrypted.** No plaintext path, send or receive.
- A config change to the vault connection ends in a reload, through `reloadAfterConfigChange()` (`src/sync/vaultConnect.ts`): the sync package keeps its root key in module state, and the reload has to wait for a shell's keystore.
- Release notes contain no em dashes (family rule). Times are Mountain Time (America/Denver).

## Verifying

- `npm run lint` (zero warnings allowed), `npm test` (unit), `npx tsc -b` (types), `npm run build` (includes the service worker). CI runs all four and builds the Docker image.
- Component files export components only (the fast-refresh lint rule). Helpers live beside them: `components/kit.ts`, `components/useEventActions.ts`, `state/data.ts`.
- `npm run test:e2e` for anything touching sync, the roster or intents. It needs the dev server and a local vault; the header of `e2e/vault-sync.mjs` has the one-liner that starts one from `../glance-vault` with `thingglance` allowed.
- Android: `./build-android.sh --webview-debug`, install on an emulator, then `node scripts/android-check.mjs emulator-5554` for anything touching the shell seams, the keystore, links or the back button (`docs/android.md`). It needs the dev server and a local vault, like `test:e2e`. **Always pass `-s emulator-5554` to `adb`**: a real phone is often plugged into this machine too, and the check wipes the app's data.
- iOS: `npm run test:ios` for anything under `ios/App/Packages`, and `npm run build:ios` then a simulator build for anything touching `ios/` or the shell seams (`docs/ios.md` has the commands, and `scripts/ios-webview.py` evaluates JavaScript in the running app). Files under `ios/` copied from lastGLANCE say so in their first line.
- Desktop: `npm run build:electron:dir`, then `npm run test:electron-smoke` for anything touching `electron/` or the bridge, and `npm run test:electron-vault` (it needs the local vault, like `test:e2e`, but not the dev server) for anything touching the desktop's network, keystore or live stream. Both run on a throwaway profile. `npm run dev:electron` is the dev loop, on port 5193.
- Dev server is on port 5190 (`.claude/launch.json`), deliberately not Vite's default so its localStorage never shares an origin with a sibling app's dev server.
